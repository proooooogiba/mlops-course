# Проверка полного набора и оптимизации

Проверено 12 октября 2026 года локально на Apple Silicon, Docker, ClickHouse **25.8.4.13**, Kafka **3.9.1**. Оба CSV загружены полностью отдельным Python producer через настоящий Kafka-топик; прямого импорта CSV в ClickHouse при загрузке не использовалось.

## Полнота и правильность

| Источник | Строк в CSV / ClickHouse | Уникальных номеров строк |
|---|---:|---:|
| train.csv | 786 431 | 786 431 |
| test.csv | 262 144 | 262 144 |
| Всего | **1 048 575** | **1 048 575** в паре с именем файла |

Для каждого файла номера записей в ClickHouse покрывают диапазон `1..N` без пропусков и дубликатов. SHA-256 исходных файлов и параметры загрузки сохранены в [`dataset_manifest.json`](dataset_manifest.json). Проверка заново прочитала CSV и вычислила максимальные транзакции средствами Python с `Decimal`.

Ответ Python совпал с обычным SQL и с SQL по агрегатам для всех **51** кодов штата/округа. Выдача — [`max_transaction_by_state.csv`](max_transaction_by_state.csv), машинный отчёт — [`full_verification.json`](full_verification.json). Например, для NE: `travel,28948.90`, для NY: `travel,27390.12`.

## Выполнение запросов

Каждый запрос прогрет один раз, затем выполнен пять раз без работающего producer. Перед замером выполнен `OPTIMIZE FINAL`; агрегированная таблица содержит 51 строку. Метрики взяты из `system.query_log`, полные серии сохранены в [`full_benchmark.json`](full_benchmark.json).

| Вариант | Медиана, ms | Прочитано строк | Прочитано байт |
|---|---:|---:|---:|
| Baseline: обычные String, LZ4, без ключа сортировки | 21 | 1 048 575 | 64 251 936 |
| Оптимизированная исходная таблица | 24 | 1 048 575 | 19 928 291 |
| AggregatingMergeTree + argMaxMerge | **2** | **51** | **7 505** |

В этом запуске агрегаты ускорили запрос относительно baseline в **10,5 раза**, сократив число прочитанных строк примерно в **20 560 раз**. Время измерено в миллисекундах на локальном стенде и не является гарантией для другой машины. Более устойчивый эффект — устранение просмотра миллиона исходных строк за счёт предагрегации.

Оптимизация только исходной таблицы уменьшила чтение байт, но **не ускорила** этот запрос в данном замере: 24 ms против 21 ms. Запрос без фильтра по времени/штату всё равно обходит все строки, а партиции и преобразования типов добавляют накладные расходы. Поэтому решение использует отдельную агрегированную таблицу именно для целевого запроса.

## Хранение

Размеры столбцовых данных после слияний (`sum(data_compressed_bytes)` из `system.parts`):

| Таблица | Сжатые данные, байт | Назначение |
|---|---:|---|
| transactions_baseline | 71 891 779 | Снимок до оптимизации для сравнения |
| transactions | **50 559 469** | Полные исходные данные после оптимизации |
| state_max | **1 295** | Дополнительные агрегаты |

Сжатый объём исходной таблицы уменьшился примерно на **29,7%**. Агрегаты занимают дополнительно 1 295 байт столбцовых данных (1 402 байта с учтёнными `system.parts.bytes_on_disk` метаданными части). Baseline создаётся только по команде benchmark; для основной работы достаточно исходной таблицы и агрегатов. Эти размеры не включают Kafka log, системные логи ClickHouse и Docker images.

## Дополнительные проверки

Прошли **17 локальных тестов** и отдельный сквозной запуск Kafka → ClickHouse на восьми синтетических транзакциях с тремя штатами. Он проверяет известные заранее ответы, в том числе отличие максимальной транзакции от суммы по категории, равенство сумм внутри одного CSV и между двумя файлами, а также десятичные суммы. Проверка обоих SQL выполнена до принудительных слияний benchmark, что подтверждает работу `argMaxMerge` без ожидания фоновых merges.

Повторить замеры: положить файлы с указанными SHA-256 в `data/`, выполнить `make up load verify benchmark` на чистом стенде. Текущие результаты появятся в `results/runtime/`, сохранённые здесь файлы при этом не перезаписываются.
